RAG-ONLY IMAGE EVIDENCE PLATFORM
High-Level Architecture & High-Level Design (HLD)
Multi-folder image browsing, tree selection, preview, parallel multimodal indexing, hybrid retrieval and evidence-grounded AI
Architecture overview: RAG-only image evidence platform
Scope: React UI + Python/FastAPI + Celery/Redis + PostgreSQL/pgvector + OpenSearch + ClickHouse + MinIO + Neo4j + local embedding/reranking/LLM/VLM services
1. Executive Summary
This HLD defines the RAG-only architecture for ingesting and searching image evidence selected from one or more folders. The user can browse folders, see folder and file names in a hierarchical tree, preview images before processing, select entire folders or individual images, and then start a controlled RAG processing job containing only the selected items.
The design keeps the previous high-performance principles: artifact-first intake, deterministic provenance and hashing, parallel CPU/GPU workers, idempotent/resumable processing, batch embeddings, pgvector HNSW, exact/full-text/vector hybrid retrieval, rank fusion, reranking, evidence-only generation, ClickHouse analytics, multi-node HA, and merge-safe database migrations.
RAG scope only. Vulnerability/scanner architecture is explicitly excluded.
Original image evidence is immutable; thumbnails, OCR, captions and embeddings are derived artifacts.
Only items present in the committed selection manifest are eligible for RAG processing.
Every retrieved image must remain traceable to case, evidence source, folder, relative file path, hash, processing version and source object URI.
AI-derived descriptions are never treated as authoritative source facts.

5. End-to-End Processing Flow
Figure 3. End-to-end sequence from selection to grounded answer
User creates or opens a case/evidence context and clicks Add Folder or Add Images.
React builds a virtual tree and lazily generates/preloads thumbnails for visible rows only.
User checks folders and/or individual images. The UI continuously recomputes tri-state parent nodes and selected byte/file counts.
On Start Processing, the client submits a versioned selection manifest. The server validates authorization, MIME/type policy and item limits.
Selected local files are streamed/multipart-uploaded; repository items are registered by immutable object/source reference.
Each image is hashed and deduplicated according to case policy. Originals are stored once; provenance remains per selection/evidence source.
Celery fans out parallel stage jobs for metadata, thumbnail, OCR, image embedding, text embedding and indexing.
Only after required stages succeed is an image marked indexed. Deterministic IDs and completion markers make retries safe.
Investigator queries are authorized to the selected case/evidence scope. Hybrid retrieval collects structured, lexical and vector candidates.
RRF/score fusion and reranking produce a small evidence set; the LLM/VLM answers from that evidence and returns image previews and citations.

6.2 Performance Controls
Batch embedding requests by model and input shape; use dynamic batch sizing based on GPU memory.
Use bounded worker concurrency to avoid storage random-I/O collapse.
Use multipart/streaming uploads; do not load entire large folders into browser memory.
Generate thumbnails only for visible/selected UI rows; cache by content hash.
Skip duplicate expensive stages when the same content hash and processing-version fingerprint already exist and policy allows reuse.
Use HNSW indexes for vectors, materialized tsvector/GIN for PostgreSQL FTS, OpenSearch BM25 for large lexical corpora, and ClickHouse for analytical filtering.
Persist stage checkpoints and completion markers. A job is not complete merely because embeddings were partially written.
Use back-pressure when object-store, database or index write latency exceeds thresholds.

8. Storage and Data Model
Figure 6. Core RAG image evidence data model
8.1 PostgreSQL / pgvector
PostgreSQL is the authoritative metadata/system-of-record database.
pgvector stores image and text embeddings; use separate vector columns or embedding rows keyed by image_id + modality + model_version.
HNSW indexes should be dimension/model specific; model changes create a new embedding version rather than mutating old evidence rows.
Selection manifests and processing checkpoints are persisted so UI state and job restarts remain deterministic.
8.2 MinIO/Object Storage
Original image objects stored under immutable case/evidence namespace; object versioning/retention enabled where required.
Thumbnails and OCR/derived artifacts stored in separate derived prefixes; never replace originals.
Presigned URLs should be short lived and authorized to case scope.
8.3 OpenSearch and ClickHouse
OpenSearch: OCR text, filenames, relative paths, EXIF fields, tags, exact and fuzzy lexical search.
ClickHouse: ingestion metrics, processing events, large filtered image metadata/timeline views, query analytics and batch candidate prefiltering.
Neither replaces PostgreSQL as the primary evidence metadata store.

9.1 Query Planning
9.2 Retrieval Fusion and Reranking
Apply authorization and case/evidence/folder/image filters before semantic retrieval wherever possible.
Gather candidates from exact/structured, PostgreSQL FTS, OpenSearch BM25, text vectors, image vectors and analytical filters.
Fuse ranks with Reciprocal Rank Fusion (RRF) or calibrated score fusion; retain per-arm score and rank for explainability.
Rerank only the top candidate set to control GPU latency. The reranker may consume query text, OCR/metadata text and image thumbnails/originals depending model capability.
Pass only top evidence records to the generation model, with citation IDs and source metadata.
9.3 Generation Guardrails
The LLM/VLM must not claim an image contains something unless the retrieved evidence or a clearly labelled visual interpretation supports it.
Every material statement should reference one or more citation IDs that resolve to the original image, relative path, hash and metadata.
Show image cards in the answer so the investigator can visually verify the supporting evidence.
Store query, filters, retrieved IDs, model versions, prompt template version, answer and reviewer disposition in the audit trail.
10. API HLD
11. Security, Authentication and Evidence Isolation
JWT/OIDC-compatible authentication with RBAC; all selection, preview, upload, search and citation requests are case scoped.
Tenant/firm isolation is enforced in PostgreSQL queries, object-store namespaces, OpenSearch filters, ClickHouse query predicates and vector retrieval metadata filters.
Do not accept arbitrary server filesystem paths from the browser. Server repository browsing operates only within pre-registered allowlisted evidence roots.
Short-lived presigned object URLs; no public bucket access.
File-type validation uses magic bytes/server decoding, not filename extension alone.
Audit all selection changes, processing starts, searches, answer generation and evidence access.
Original source images are never mutated by OCR, thumbnailing, model preprocessing or user annotations.
12. Migration and Schema Evolution
The RAG-only module must use the existing merge-safe migration behavior so new tables, columns and indexes are added without dropping existing evidence. Startup/deployment migration should be serialized by a PostgreSQL advisory lock in HA environments.
CREATE TABLE IF NOT EXISTS for new RAG selection/image/processing tables.
ALTER TABLE ... ADD COLUMN IF NOT EXISTS for additive schema changes.
CREATE INDEX IF NOT EXISTS for FTS, JSONB, lookup and HNSW indexes.
Version embedding schemas by model/version; never reinterpret an old vector as a new-model vector.
Record migration checksum, status and application version in schema migration history.

17. Frontend HLD Details
17.1 Large Tree Performance
Use virtualized rendering (for example react-window/react-virtuoso style architecture) so only visible rows are mounted.
Do not decode full-resolution images for tree rows; use cached thumbnails.
Debounce tree search/filter operations and precompute lowercase searchable names/paths.
For server repository mode, page or lazy-load folder children rather than returning the entire filesystem tree in one response.
Use Web Workers only for client-side hashing/metadata if required and supported; heavy forensic processing remains server-side.
18. Processing Profiles
The UI should show the selected processing profile before Start Processing so the investigator understands latency/cost implications. Profiles never change the preserved original evidence.

Appendix B. Design Baseline From Previous Forensic Architecture
This design carries forward the earlier principles that raw evidence is processed deterministically before semantic retrieval, that hybrid retrieval is mandatory for exact forensic identifiers, that parallel workers and batching are used for performance, and that structured/full-text/vector stores serve different workloads. The image-specific design adds a user-controlled folder/file selection manifest and multimodal image retrieval while preserving those principles.

Failure | Required behavior
Browser closed before Start | No server processing unless a manifest/job was committed; local selection may be restored only from persisted session metadata where possible.
Upload interrupted | Multipart upload resumes from acknowledged parts; incomplete objects are not indexed.
Worker crash | Celery retry using deterministic stage ID; existing completed stage output reused if fingerprint matches.
GPU unavailable | Queue remains pending or routes to another GPU node; CPU fallback only if explicitly configured.
Index service unavailable | Persist durable “index pending” state; do not mark image complete.
OCR/model failure | Record stage failure and model/parser error; allow retry or policy-based partial completion.
Database migration race | Advisory lock ensures one migration executor at a time.
Duplicate image | Record separate provenance/selection reference while optionally reusing derived artifacts keyed by hash + processing version.
